# Profilarr v2 serialized output contract

**Ticket context:** `.scratch/profilarr-v2-support/issues/01-research-v2-output-contract.md`
**Research date:** 2026-11-19

## Bottom line

Profilarr Compliant Databases (PCDs) are repositories of a JSON manifest plus ordered SQL operations, not a final SQLite file or a directory of standalone YAML/JSON profiles. The schema repository defines the relational tables and their constraints; `trash-pcd` supplies TRaSH-derived data as generated SQL and declares the schema dependency in its manifest. For a TrashGuides generator, the important output is therefore a PCD repo: `pcd.json`, SQL inserts/operations using schema table and column names, and any optional tweaks. [Schema structure](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/docs/structure.md) · [`trash-pcd` manifest](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/pcd.json) · [generated base SQL](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/ops/1.initial.sql)

## Documented contract

### Package and operation format

- Every PCD has a root `pcd.json`. The manifest specification requires `name`, semver `version`, `description`, a `dependencies` object, and `profilarr.minimum_version`. Names are described as unique identifiers (lowercase, hyphens preferred); all PCDs must depend on `schema` at minimum. Optional manifest fields are `arr_types`, `authors` (name, optional email), `license`, `repository`, `tags`, and `links`. [`schema/docs/manifest.md`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/docs/manifest.md)
- The example sets `profilarr.minimum_version` to `2.0.0`. In the inspected `trash-pcd` manifest, the package is `trash-pcd` version `1.0.37`, supports Radarr and Sonarr, depends on schema `1.1.0`, and also declares authors, MIT, repository, tags, homepage, and issues links. Its dependency object uses the full schema GitHub URL as its key: `"https://github.com/Dictionarry-Hub/schema": "1.1.0"`. [`schema/pcd.json`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/pcd.json) · [`trash-pcd/pcd.json`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/pcd.json)
- A PCD is operational SQL: operations are ordered and replayable, and target relational tables so foreign keys apply. The documented layout is a manifest, `ops/` operations, and optionally `tweaks/`; the schema is a separate layer containing DDL, with no data. [`schema/docs/structure.md`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/docs/structure.md)
- `trash-pcd` demonstrates this as `ops/1.initial.sql` plus subsequent numbered SQL updates (for example `ops/100...sql` onward); its initial file is explicitly labeled generated by `trash-conv` and contains `INSERT INTO ...` statements, not schema DDL. Its sync workflow invokes the converter with TRaSH Guides as input, `trash-pcd` as output, and schema as the schema source (`-i`, `-o`, `-s`). [`trash-pcd/ops/1.initial.sql`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/ops/1.initial.sql) · [`trash-pcd/.github/workflows/sync.yml`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/.github/workflows/sync.yml)
- The `trash-pcd` README describes `main` as Standard/Anime/SQP, with separate `french` and `german` branches, and says a branch can be selected when adding the repo to Profilarr. [`trash-pcd/README.md`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/README.md)

### Relational model relevant to TrashGuides generation

The base schema is defined in [`schema/ops/0.schema.sql`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/ops/0.schema.sql). The concise field inventory below names the data fields; most tables also have generated `id` and/or `created_at` / `updated_at` columns. The DDL supplies defaults for those generated values, and `trash-pcd`'s inserts commonly omit them.

| Purpose | Tables and data fields | Relationships / meaning |
|---|---|---|
| Reusable reference data | `tags(name)`; `languages(name)`; `regular_expressions(name, pattern, regex101_id, description)`; `qualities(name)` | Names are unique keys. Regex rows carry a required pattern and optional regex101 ID/description. Canonical qualities can be mapped to app-specific API names. |
| Quality name mapping | `quality_api_mappings(quality_name, arr_type, api_name)` | Primary key `(quality_name, arr_type)`; `quality_name` references `qualities(name)`. Missing mapping means the quality does not exist for that app. |
| Custom formats | `custom_formats(name, description, include_in_rename)`; `custom_format_conditions(custom_format_name, name, type, arr_type, negate, required)` | Format names are unique. Each condition belongs to a format by name; `(custom_format_name, name)` is unique. `arr_type` defaults to `all`; `negate` and `required` default to false/0. |
| Condition payloads | `condition_patterns(..., regular_expression_name)`; `condition_languages(..., language_name, except_language)`; `condition_indexer_flags(..., flag)`; `condition_sources(..., source)`; `condition_resolutions(..., resolution)`; `condition_quality_modifiers(..., quality_modifier)`; `condition_sizes(..., min_bytes, max_bytes)`; `condition_release_types(..., release_type)`; `condition_years(..., min_year, max_year)` | Each child row keys back to `(custom_format_name, condition_name)`. Pattern and language payloads also reference regex/language names. Bounds may be NULL. |
| Profiles and quality order | `quality_profiles(name, description, upgrades_allowed, minimum_custom_format_score, upgrade_until_score, upgrade_score_increment)`; `quality_groups(quality_profile_name, name)`; `quality_group_members(quality_profile_name, quality_group_name, quality_name)`; `quality_profile_qualities(quality_profile_name, quality_name, quality_group_name, position, enabled, upgrade_until)` | Groups are profile-local. A profile quality row is ordered by `position` and points to either one quality or one group. Group membership is profile-scoped. |
| Associations | `regular_expression_tags(regular_expression_name, tag_name)`; `custom_format_tags(custom_format_name, tag_name)`; `quality_profile_tags(quality_profile_name, tag_name)`; `quality_profile_languages(quality_profile_name, language_name, type)`; `quality_profile_custom_formats(quality_profile_name, custom_format_name, arr_type, score)` | Composite primary keys prevent duplicate associations; tag/language and profile/format references use names. Custom-format scores are profile- and app-specific. Language `type` is documented as `must`, `only`, `not`, or `simple`. |
| Optional media-management data | `radarr_quality_definitions` / `sonarr_quality_definitions(name, quality_name, min_size, max_size, preferred_size)`; `radarr_naming(name, rename, movie_format, movie_folder_format, replace_illegal_characters, colon_replacement_format)`; `sonarr_naming(name, rename, standard_episode_format, daily_episode_format, anime_episode_format, series_folder_format, season_folder_format, replace_illegal_characters, colon_replacement_format, custom_colon_replacement_format, multi_episode_style)`; `radarr_media_settings` / `sonarr_media_settings(name, propers_repacks, enable_media_info)`; `delay_profiles(name, preferred_protocol, usenet_delay, torrent_delay, bypass_if_highest_quality, bypass_if_above_custom_format_score, minimum_custom_format_score)` | Size definitions reference canonical qualities. Naming/settings are app-specific. Delay profiles encode protocol preference and conditional delays. |
| Optional test fixtures | `custom_format_tests(custom_format_name, title, type, should_match, description)`; `test_entities(type, tmdb_id, title, year, poster_path)`; `test_releases(entity_type, entity_tmdb_id, title, size_bytes, languages, indexers, flags)` | These support matcher/profile testing; release `languages`, `indexers`, and `flags` are JSON-array text, defaulting to `[]`. |

### Validation and integrity rules

The schema DDL declares the relational rules for primary/unique keys, `NOT NULL`, foreign keys, `CHECK`s, defaults, and indexes (foreign-key checks apply when SQLite FK enforcement is enabled). Important rules for generated profile data:

- References use stable natural keys (principally entity names and composite name keys), not generated integer IDs. Foreign keys cascade on delete/update. The schema changelog calls out this shift as necessary for correct links after recompiling operations. [`schema/ops/0.schema.sql`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/ops/0.schema.sql) · [`schema/CHANGELOG.md`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/CHANGELOG.md)
- A `quality_profile_qualities` row must set exactly one of `quality_name` or `quality_group_name`; its `position` is required. `upgrade_until_score` is profile data, while at most one row per profile can have `upgrade_until = 1` (partial unique index). The schema comment says every quality must be represented directly or through a group.
- `quality_groups` are unique by `(quality_profile_name, name)`. Profile-to-custom-format scoring is unique by `(quality_profile_name, custom_format_name, arr_type)`. Profile, group, format, condition, and tag/language references must resolve to existing name keys.
- `quality_profiles.upgrade_score_increment` must be greater than zero. Radarr colon replacement is restricted to `delete`, `dash`, `spaceDash`, `spaceDashSpace`, or `smart`; Radarr/Sonarr `propers_repacks` is restricted to `doNotPrefer`, `preferAndUpgrade`, or `doNotUpgradeAutomatically`.
- Delay-profile protocol is one of `prefer_usenet`, `prefer_torrent`, `only_usenet`, `only_torrent`. `usenet_delay` must be NULL exactly for `only_torrent`; `torrent_delay` must be NULL exactly for `only_usenet`. `minimum_custom_format_score` must be NULL when bypass-by-score is off, and non-NULL when it is on.
- The schema comments specify that each custom-format condition has a type-specific payload, and that each condition should occur in only one payload table. The DDL enforces the child-to-condition foreign key and one row per child table for a condition, but has no cross-table constraint that proves the payload table matches `custom_format_conditions.type`. That matching is therefore a generator-level semantic validation.
- `arr_type` conventions are documented in SQL comments (`radarr`, `sonarr`, `all`), but are not generally guarded by `CHECK` constraints. Likewise, the `quality_profile_languages.type` values are documented in a comment without a SQL enum check. A generator should validate these values itself rather than assume the database rejects every bad string.
- The schema repo's published validation workflow runs language and quality checks. Its scripts compare schema language/quality entries against upstream Radarr and Sonarr sources; they are not a complete validator for arbitrary generated SQL or all profile semantics. [`schema/.github/workflows/validate.yml`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/.github/workflows/validate.yml) · [`validateLanguages.sh`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/scripts/validateLanguages.sh) · [`validateQualities.sh`](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/scripts/validateQualities.sh)

## What `trash-pcd` concretely emits

The `trash-pcd` sync workflow checks out TRaSH Guides, the schema, and `trash-conv`, then runs the converter with those repositories as input/schema/output context. It writes generated data to the existing PCD checkout; `ops/1.initial.sql` starts with reusable tags and regex rows and continues with relational SQL inserts. The manifest declares schema compatibility separately. This is a concrete example of the expected boundary: conversion logic emits data operations against the shared schema; it does not define a competing profile JSON object format. [`sync.yml`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/.github/workflows/sync.yml) · [`ops/1.initial.sql`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/ops/1.initial.sql)

## Source caveats and inference

- **Documented-source mismatch:** `schema/docs/structure.md` says dependencies are reserved for future use and not part of 2.0, while the manifest spec says dependencies are required and every PCD must depend on schema; the current `trash-pcd` manifest does declare that schema dependency. For compatibility with the actual example and manifest specification, include the schema dependency. Treat the structure page's dependency paragraph as stale or unresolved unless Profilarr maintainers clarify it. [Structure](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/docs/structure.md) · [Manifest spec](https://github.com/Dictionarry-Hub/schema/blob/e1c2bd73d7003f254ad135eeefbbed7b47f095b1/docs/manifest.md) · [`trash-pcd/pcd.json`](https://github.com/Dictionarry-Hub/trash-pcd/blob/2322a61e1194bc75140abfd305ed0070e4d79881/pcd.json)
- **Inference:** A generator intended to match `trash-pcd` should render deterministic, ordered SQL inserts into these shared tables, use names as foreign-key references, and emit the required manifest. It should retain the source distinction between app-specific `arr_type` data, preserve quality ordering/groups, and turn custom-format conditions into their typed payload tables.
- The supplied v2 website URL is a client-rendered app shell in the fetched HTML; it does not itself expose a static serialization specification there. The concrete contract above is consequently grounded in the schema docs/DDL and the example PCD source. [v2 site](https://v2.dictionarry.dev/)
